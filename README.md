# bfportal.gg prototype

A TypeScript rewrite of [bfportal.gg](https://bfportal.gg), built with TanStack Start,
SolidJS and Postgres.

bfportal.gg is where the Battlefield Portal community shares what it makes: custom
experiences for Battlefield 6 and Battlefield 2042, each with its Portal share code,
templates others can build on, snippets of script, update posts, and playtests. The
rewrite replaces the current Django site with the same features and a few new ones.

## Requirements

- Node 22.12 or newer
- pnpm 11
- Docker or Podman with a compose plugin, for the local Postgres

## Getting started

```bash
pnpm install
cp .env.example .env.local   # then fill in BETTER_AUTH_SECRET
pnpm db:up                   # Postgres 18 on localhost:5433
pnpm db:migrate
pnpm db:seed                 # sample content, so the pages are not empty
pnpm dev
```

The dev server runs on http://localhost:3000, and http://localhost:3000/api/health
reports whether it can reach the database.

Signing in needs a Discord OAuth application. Put its client id and secret in
`.env.local` and add `http://localhost:3000/api/auth/callback/discord` as a redirect
URI. Without them the site still runs in development and `/login` answers that Discord
login is not configured.

## Contributing

1. **Find a card.** Each piece of work is an
   [issue](https://github.com/battlefield-portal-community/bfportal.gg-v2/issues). Filter
   by label for an area: `public` (pages anyone sees), `writes` (forms and what they
   change), `admin`, `accounts`, `import`, `edges` (API, feeds, jobs), `ops`, `tests`,
   `design`. New here? Start with
   [`good first issue`](https://github.com/battlefield-portal-community/bfportal.gg-v2/labels/good%20first%20issue).
   `next` marks what matters most now.
2. **Check it is not blocked.** Cards labeled `decision` are questions still to
   settle, and each says which cards it blocks. Leave a blocked card until its
   decision is closed.
3. **Claim it.** Comment on the issue before you start, so two people do not build
   the same thing. A card someone has claimed and not touched for two weeks is free
   again.
4. **Read before you build.** Each card names the part of `PLAN.md` it comes from.
   Read that, and `AGENTS.md`, which has the project's words (a "template", a
   "snippet", a "playtest") and its rules for components, writes and tests.
5. **Open a pull request** that says `Closes #<number>`, with the four checks passing:
   `pnpm lint:fix`, `pnpm typecheck`, `pnpm test` and `pnpm build`. For a page,
   include screenshots at a phone width and a desktop one.

Questions go to the community [Discord](https://discord.bfportal.gg/). If you find
more work while building, open an issue for it rather than adding it to the plan.

The mockups the pages are built from are not in this repository, since their artwork
is not ours to publish. Ask on Discord for a copy.

## Scripts

| Script | Purpose |
|---|---|
| `pnpm dev` | Dev server with hot reload |
| `pnpm build` | Production build into `.output/` |
| `pnpm start` | Run the production build |
| `pnpm typecheck` | Type-check without emitting |
| `pnpm lint` | Check formatting, lint rules and import order with Biome |
| `pnpm lint:fix` | Apply Biome's fixes |
| `pnpm test` | Run the tests; needs the local Postgres |
| `pnpm db:up` | Start the local Postgres container |
| `pnpm db:generate` | Write a migration from changes to the schema |
| `pnpm db:migrate` | Apply pending migrations |
| `pnpm db:seed` | Empty the content tables and fill them with sample data. Local databases only |
| `pnpm auth:generate` | Regenerate Better Auth's tables after changing the auth configuration |

## Layout

| Path | Contents |
|---|---|
| `src/routes` | Pages and HTTP endpoints |
| `src/components` | Shared Solid components |
| `src/functions` | Server functions: how client code calls into `src/server` |
| `src/server` | Database, auth and configuration. Server only |
| `src/shared` | Types and constants used on both sides |
| `tests` | Test database setup |

Client code must not import from `src/server`. A route may use it inside its
`server.handlers`, and anything else goes through a server function in
`src/functions`. `pnpm build` fails with a trace when the rule is broken, which keeps
the database driver and secrets out of the browser bundle.

`src/routeTree.gen.ts` is generated by the Vite plugin during `pnpm dev` and
`pnpm build`. It is committed so a fresh clone can type-check. Do not edit it by hand,
and run one of the two after adding a route before type-checking.

## Configuration

`src/server/env.ts` validates the environment and is the only place server code reads
it from. The server checks it at startup and refuses to start if a variable is missing
or malformed.

Outside production, `.env.local` is loaded for the dev server, the tests, the
migrations and the auth generator. In production nothing reads an env file: the server
takes its configuration from the environment, and the Discord credentials are
required.

## Database

- The schema is `src/server/db/schema.ts`; migrations are in
  `src/server/db/migrations`.
- `src/server/db/auth-schema.ts` holds Better Auth's tables and is generated. To add a
  field to the user, declare it under `user.additionalFields` in
  `src/server/auth/index.ts`, then run `pnpm auth:generate` and `pnpm db:generate`.
- Better Auth's tables use timestamps without a time zone. Use `timestamptz` in the
  site's own tables.
- The local Postgres is published on `127.0.0.1:5433` so the old site's dev database
  can keep 5432. The one-off import reads the old one through `LEGACY_DATABASE_URL`.

## Tests

`pnpm test` recreates a `bfportal_test` database on the local Postgres, applies the
migrations and runs the tests against it. The development database is not touched.

The login tests run the whole Discord sign-in through Better Auth with Discord's two
endpoints faked, so they cover what a real login writes to the database.
